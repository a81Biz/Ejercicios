### 3.1  The Startup Class and Application Pipeline

In ASP.NET Core, `Startup` configures services and the HTTP request pipeline.

#### Structure

```csharp
public class Startup
{
    public void ConfigureServices(IServiceCollection services)
    {
        services.AddControllers();
        services.AddDbContext<AppDbContext>();
    }

    public void Configure(IApplicationBuilder app, IWebHostEnvironment env)
    {
        if (env.IsDevelopment()) app.UseDeveloperExceptionPage();

        app.UseHttpsRedirection();
        app.UseRouting();
        app.UseAuthorization();

        app.UseEndpoints(endpoints =>
        {
            endpoints.MapControllers();
        });
    }
}
```

#### Explanation

* `ConfigureServices()` registers dependencies with the DI container.
* `Configure()` defines the HTTP pipeline through middleware components.
* Middleware order is crucial: each component can process and pass requests down the pipeline.

#### Senior Insight

Treat Startup as your application’s composition root.
Avoid placing business logic there—limit it to service registration and pipeline configuration.

### 3.2  Middleware and Pipeline Composition

A **middleware** component handles HTTP requests and responses in a chain of responsibility.

#### Custom Middleware Example

```csharp
public class LoggingMiddleware
{
    private readonly RequestDelegate _next;

    public LoggingMiddleware(RequestDelegate next) => _next = next;

    public async Task InvokeAsync(HttpContext context)
    {
        Console.WriteLine($"Request: {context.Request.Path}");
        await _next(context);
        Console.WriteLine($"Response: {context.Response.StatusCode}");
    }
}
```

Registered as:

```csharp
app.UseMiddleware<LoggingMiddleware>();
```

#### Senior Insight

Middleware must be **stateless** and **thread-safe**.
Order matters: authentication → authorization → custom logic → routing → endpoints.
Insert diagnostic middleware early to capture exceptions and latency metrics.

### 3.3  Dependency Injection and Service Lifetimes

ASP.NET Core provides built-in DI through `IServiceCollection`.

| Lifetime      | Behavior                                | Typical Use                              |
| :------------ | :-------------------------------------- | :--------------------------------------- |
| **Transient** | New instance every time requested       | Lightweight, stateless services.         |
| **Scoped**    | One instance per HTTP request scope     | Database contexts, unit of work.         |
| **Singleton** | Single instance for entire app lifetime | Configuration, caching, heavy resources. |

#### Example

```csharp
services.AddTransient<IEmailSender, EmailSender>();
services.AddScoped<IRepository, Repository>();
services.AddSingleton<ICache, MemoryCache>();
```

#### Singleton Depending on Scoped

This is **not supported** directly. A singleton cannot consume scoped services because the scoped lifetime is shorter.
To resolve it:

* Inject `IServiceProvider` and create scopes manually when necessary, or
* Redesign to invert the dependency.

#### Senior Insight

Understand service lifetimes to avoid **memory leaks** and **captured state**.
Injecting a scoped service into a singleton leads to invalid object references after the request ends.

### 3.4  Configuration and Options Pattern

Configuration is centralized through `appsettings.json` and bound to typed classes.

#### Example

```json
{
  "AppSettings": { "ApiKey": "12345" }
}
```

```csharp
public class AppSettings { public string ApiKey { get; set; } }

services.Configure<AppSettings>(Configuration.GetSection("AppSettings"));
```

Injected via:

```csharp
public class SampleService
{
    private readonly AppSettings _settings;
    public SampleService(IOptions<AppSettings> options) => _settings = options.Value;
}
```

#### Senior Insight

Use `IOptionsSnapshot` for per-request reloadable settings and `IOptionsMonitor` for runtime updates.
Keep secrets in Azure Key Vault or environment variables—never in source control.

### 3.5  Logging and Monitoring in ASP.NET Core

The logging abstraction (`ILogger<T>`) supports structured logging across providers (Console, Application Insights, Seq).

#### Example

```csharp
_logger.LogInformation("User {UserId} logged in at {Time}", userId, DateTime.UtcNow);
```

#### Senior Insight

* Use **structured logging** with templates instead of string concatenation.
* Configure **log levels** per category to control verbosity.
* Export telemetry to Azure Monitor or Application Insights for distributed tracing.

### 3.6  Configuration of CORS and Security Headers

#### CORS

```csharp
services.AddCors(options =>
{
    options.AddPolicy("AllowSpecific",
        builder => builder.WithOrigins("https://client.example.com")
                          .AllowAnyHeader()
                          .AllowAnyMethod());
});
app.UseCors("AllowSpecific");
```

#### Security Headers

Use middleware or NGINX to add:

```
Strict-Transport-Security
X-Content-Type-Options
X-Frame-Options
Content-Security-Policy
```

#### Senior Insight

Enforce HTTPS, validate JWT tokens, and sanitize all user input. Security must be handled as a cross-cutting concern.

### 3.7  Hosting and Kestrel Server

ASP.NET Core applications run on **Kestrel**, a cross-platform web server built for performance.

#### Example

```csharp
public static IHostBuilder CreateHostBuilder(string[] args) =>
    Host.CreateDefaultBuilder(args)
        .ConfigureWebHostDefaults(webBuilder =>
        {
            webBuilder.UseStartup<Startup>();
            webBuilder.UseKestrel(options =>
            {
                options.Limits.MaxRequestBodySize = 10 * 1024 * 1024;
            });
        });
```

#### Senior Insight

Use Kestrel behind a reverse proxy (NGINX or Azure Front Door) for TLS termination and load balancing.
Fine-tune connection limits and request size for high-throughput APIs.

### 3.8  Azure Fundamentals for . NET Developers

#### Key Services

| Category   | Service                       | Purpose                               |
| :--------- | :---------------------------- | :------------------------------------ |
| Compute    | App Service / Azure Functions | Host web and serverless apps.         |
| Storage    | Blob Storage / Files          | Durable object storage.               |
| Database   | SQL Database / Cosmos DB      | Relational and NoSQL stores.          |
| Messaging  | Service Bus / Event Grid      | Decoupled asynchronous communication. |
| Monitoring | Application Insights          | Telemetry and diagnostics.            |

#### Service Bus Example

```csharp
await using var client = new ServiceBusClient(connectionString);
ServiceBusSender sender = client.CreateSender(queueName);
await sender.SendMessageAsync(new ServiceBusMessage("Hello Azure"));
```

#### Senior Insight

Design for **idempotency** and **retry** when using messaging.
Leverage Azure Managed Identities to authenticate securely without storing keys.

### 3.9  Scalability and Performance on Azure

#### Vertical vs Horizontal Scaling

* **Vertical:** Increase CPU and RAM of existing nodes.
* **Horizontal:** Add more instances behind a load balancer.

#### Strategies

* Use **Auto-Scaling Rules** based on CPU or queue length.
* Implement **Caching** with Azure Redis Cache.
* Employ **CDN** for static content delivery.
* Adopt **Async I/O** to maximize thread utilization.

#### Senior Insight

Always measure before scaling. Identify CPU, memory, or I/O bottlenecks through Application Insights metrics and profilers.

### 3.10  Continuous Integration and Delivery (CI/CD)

#### YAML Pipeline Sample (GitHub Actions)

```yaml
name: Build and Deploy

on: [push]

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v3
      - name: Setup .NET
        uses: actions/setup-dotnet@v3
        with:
          dotnet-version: 8.0.x
      - run: dotnet restore
      - run: dotnet build --configuration Release
      - run: dotnet test
      - run: dotnet publish -c Release -o out
      - uses: azure/webapps-deploy@v2
        with:
          app-name: my-app
          package: out
```

#### Senior Insight

Adopt **Infrastructure as Code** for repeatable deployments.
Integrate security scans and linting into the pipeline.
Keep builds deterministic by pinning dependency versions.
